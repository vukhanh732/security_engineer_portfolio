Log4Shell: why one logging call became a global incident

What happened

In December 2021, a critical flaw was disclosed in Log4j, a Java logging library used across an enormous share of enterprise software. A specially crafted string logged by an application could make the server reach out to an attacker-controlled server and execute arbitrary code, with no authentication required.

The likely technical root cause

Log4j's message-lookup feature evaluated JNDI expressions embedded in logged strings. If any user-controllable value — a request header, a username, a form field — ended up in a log line, Log4j would try to resolve it, including reaching out over LDAP or RMI to a remote server and loading whatever class it returned. The core failure was treating logged, attacker-influenced text as something safe to actively evaluate rather than passively record. Logging is meant to be a read-only sink; here it became an execution path.

What I'd build to detect or prevent this

Detection at the edge: a WAF-style rule flagging JNDI-lookup patterns (${jndi:) in any inbound header or parameter — the same URL-decode-before-match discipline I used for SQL injection detection in SentryNode, since encoded variants are the obvious bypass. At the pipeline level, this is exactly what Gatekeeper's dependency scanning is for: a known-CVE library version should fail the build before it ever reaches production, not get caught after an incident.
