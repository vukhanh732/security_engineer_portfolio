Log4Shell: why one logging call became a global incident

The lesson: data sent to a logging system must stay data. Inventory dependencies, patch quickly, and watch for unexpected outbound callbacks.

What happened

Log4Shell, disclosed in December 2021, affected Log4j Core versions that evaluated JNDI lookups inside log messages. An attacker only needed to place a crafted string in input the application would log, such as a header or username. The server could then contact attacker-controlled infrastructure and load code.

Why the design failed

A passive observability path became an execution path. Log4j combined attacker-influenced text, automatic expression evaluation, and network-capable JNDI resolution. That turned one logging call into unauthenticated remote code execution.

How this maps to MITRE ATT&CK

T1190Exploit Public-Facing Application: deliver the lookup through any input the application logs.
T1071 / T1105Application Layer Protocol / Ingress Tool Transfer: call out to attacker infrastructure and retrieve a payload.

What I would build

First, an asset and dependency inventory that can answer where Log4j Core is running, including inside vendor products. Next, edge detection for decoded JNDI patterns plus egress alerts for unusual LDAP, RMI, or DNS callbacks from application servers. Finally, dependency scanning in Gatekeeper and matching telemetry in SentryNode. Detection supports patching; it does not replace it.
